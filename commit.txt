fix(setup macros): simplify import/export filters; default to UniKey `.txt`

## Why

The **“All supported formats”** file filter duplicated every extension (`*.txt`, `*.json`, …)
in one entry. Choosing it did **not** change how files are decoded: interchange format still
comes from **`MACRO_INTERCHANGE_FORMAT_AUTO`** and **`MacroFormatHandlerRegistry::detect_from_path`**
(on the pathname suffix). GTK filters only constrain what the dialog tends to highlight and—on
export—which **preferred extension** `macro_export_filename_finalize_for_save` applies from
`macro_file_chooser_filter_preferred_export_extension`.

Keeping a catch-all filter was therefore misleading: users might think one must pick “all” to
import mixed types, while in practice suffix-based dispatch handles every supported type the same.

Defaulting explicitly to **UniKey macro text** aligns the UI with the most common workflow and
matches export behavior already implied by tagging that filter with **`.txt`**. Other formats remain
available as explicit filters (`JSON macros`, YAML, plist, CSV, TSV).

## What changed

- **`setup/macro_file_io.cpp`**
  - Removed the aggregated “All supported formats” `GtkFileFilter`.
  - **Default active filter** is now **UniKey macro text** (`.txt` / `.macro` patterns), unchanged
    preferred extension tagging for export (still `.txt` for that filter).
- **`tests/macros/macro_file_io_test.cpp`**
  - Renamed the combined AUTO-import regression test path from
    `/ui/macros/file-io/all-supported-filter-still-uses-filename-extension` to
    **`/ui/macros/file-io/auto-import-resolves-by-filename-extension`**, since the assertion is only
    that basename suffix selects the codec, not interaction with any “all formats” GTK filter.
